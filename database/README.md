# Database (Member 2)

Centralized PostgreSQL persistence for scans, resources, and findings,
hosted on Supabase. This module owns storage only — it has no opinion on
how scans are triggered (Member 3 / FastAPI) or how findings get their
severity/risk_score (Member 1's scanner + risk engine).

## Schema

Three tables, matching PRD section 8:

**`scans`**
| column | type | notes |
|---|---|---|
| id | UUID (PK) | generated app-side (`uuid.uuid4()`) |
| started_at | timestamptz | defaults to now() |
| completed_at | timestamptz | null until the scan finishes |
| status | enum: RUNNING / COMPLETED / FAILED | |
| total_resources | int | |
| total_findings | int | |
| total_risk_score | int | sum of all finding risk_scores |

**`resources`**
| column | type | notes |
|---|---|---|
| id | UUID (PK) | |
| scan_id | UUID (FK -> scans.id, cascade delete) | |
| service | string | `"s3"`, `"ec2"`, `"iam"` |
| resource_id | string | bucket name, instance ID, IAM username |
| region | string, nullable | `"global"` for IAM |
| configuration | JSON | raw collected config, e.g. `{"mfa_enabled": false}` |
| created_at / updated_at | timestamptz | |

**`findings`**
| column | type | notes |
|---|---|---|
| id | UUID (PK) | |
| scan_id | UUID (FK -> scans.id, cascade delete) | |
| resource_pk | UUID (FK -> resources.id, cascade delete) | the *row*, not the resource_id string |
| rule_id | string | e.g. `"IAM_MFA"` |
| service, resource_id | string | denormalized copies from the finding contract, so findings are queryable without a join |
| severity | enum: CRITICAL / HIGH / MEDIUM / LOW / INFO | |
| status | enum: PASS / FAIL | |
| message, description, remediation | string | |
| risk_score | int | computed by Member 1's Risk Engine |
| created_at | timestamptz | |

Indexes exist on every column the PRD's filterable endpoints need
(`severity`, `service`, `status`, `rule_id`, both foreign keys), plus a
composite index on `resources(service, resource_id)` for the lookup
`persist_scan` does while linking findings to their resource row.

Deletes cascade: deleting a scan removes its resources and findings, both
at the ORM level (`cascade="all, delete-orphan"`) and at the DB level
(`ON DELETE CASCADE`), so this holds even if a row is ever deleted outside
the app (e.g. from the Supabase table editor).

## Setup

1. Install dependencies:
   ```
   pip install -r database/requirements.txt
   ```
2. Copy `.env.example` to `.env` and fill in your real Supabase **Session
   pooler** connection string (Supabase dashboard → Project Settings →
   Database → Connection String → "Session pooler" tab). It looks like:
   ```
   postgresql+psycopg2://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
   ```
   `database/connection.py` will refuse to start if `DATABASE_URL` is
   still the bare `https://<ref>.supabase.co` project URL — that's the
   API URL, not a Postgres connection string.
3. Create the schema. Two options:
   - **Alembic (recommended, what the team should use going forward):**
     ```
     alembic upgrade head
     ```
   - **Quick local check only:**
     ```
     python -m database.init_db
     ```
4. Verify everything works end-to-end without needing AWS or the scanner:
   ```
   python -m database.seed_demo
   ```
   This persists a sample scan (using the exact `IAM_MFA` finding from
   PRD section 12) and reads it back through the same CRUD functions
   Member 3's API will call.

## Making schema changes later

```
# after editing database/models.py
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```
Always review the autogenerated migration before running it — Alembic's
diffing isn't perfect, especially around enum changes.

## What Member 3 (backend) should use

- `database.connection.get_db` — FastAPI dependency (`Depends(get_db)`)
  that yields a session and closes it after the request.
- `database.crud` — all read/write operations: `create_scan`,
  `complete_scan`, `list_scans`, `get_scan`, `list_resources`,
  `list_findings` (filters by `severity` / `service` / `status`),
  `get_finding_with_resource`, `get_dashboard_summary`.
- `database.persistence.persist_scan(scan_results, calculated_findings)`
  — the one call that takes Member 1's scan output + risk-scored findings
  and writes a complete scan (this is what `POST /scan` should call after
  running the scanners).
- `database.serializers` — optional `*_to_dict()` helpers if you don't
  want to hand-write Pydantic response models from scratch.

## Integration contract

`persist_scan` takes:
- `scan_results`: objects with `.service`, `.resource_id`, `.region`,
  `.configuration` (whatever Member 1's `ScanResult` looks like — we
  duck-type this rather than importing his module directly, see the
  comment in `persistence.py` for why).
- `calculated_findings`: list of dicts shaped exactly like PRD section 12:
  ```json
  {"rule_id": "IAM_MFA", "service": "iam", "resource_id": "harsh",
   "severity": "HIGH", "status": "FAIL",
   "message": "IAM user does not have MFA enabled.",
   "description": "...", "remediation": "Enable MFA...", "risk_score": 7}
  ```
  This is exactly what `RiskEngine.calculate_findings()` already
  produces, so `POST /scan` should be a straight pipe: scanners →
  analyzers → risk engine → `persist_scan`.

## Security

- `.env` is git-ignored; only `.env.example` (no real credentials) is
  committed.
- Never put the DB password in `alembic.ini` — `alembic/env.py` reads it
  from `DATABASE_URL` via `database/connection.py` at runtime.
